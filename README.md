# dynamokv

A scaled-down, security-hardened reimplementation of Amazon's Dynamo — a highly available, partition-tolerant key-value store — built phase by phase from the 2007 Dynamo paper's core ideas, then hardened with a real security layer and red-teamed against it.

## Architecture

```mermaid
flowchart LR
    subgraph Client-facing
        C[Client] -->|"Bearer token, HTTPS\n/v1/keys/{key}"| P1["node-1 :8000\n(public API)"]
    end

    subgraph "Cluster (mTLS between nodes)"
        P1 -->|"quorum fan-out\nW=2/R=2 of N=3"| I1["node-1 :8443\n(internal)"]
        P1 -.->|mTLS| I2["node-2 :8443\n(internal)"]
        P1 -.->|mTLS| I3["node-3 :8443\n(internal)"]
        I1 <-.->|gossip + hinted handoff| I2
        I2 <-.->|gossip + hinted handoff| I3
        I1 <-.->|gossip + hinted handoff| I3
    end

    I1 --> S1[("AES-256-GCM\nSQLite")]
    I2 --> S2[("AES-256-GCM\nSQLite")]
    I3 --> S3[("AES-256-GCM\nSQLite")]

    subgraph Ops (unpublished ports)
        M1["node-1 :9090\n/metrics"]
        M2["node-2 :9090\n/metrics"]
        M3["node-3 :9090\n/metrics"]
    end
    Prom[Prometheus scraper] -.->|compose-network only| M1 & M2 & M3
```

Each node runs three independent servers in one process:
- **Public** (`:8000`, published to the host) — the client-facing, versioned `/v1/keys/{key}` API. Server-only TLS, bearer-token auth, per-namespace ACLs, audit logging.
- **Internal** (`:8443`, never published) — node-to-node replica traffic, gossip, and hinted handoff. Requires a client certificate signed by the cluster CA (mTLS); never token-gated.
- **Metrics** (`:9090`, never published) — Prometheus `/metrics`, plain HTTP, no auth. Unreachable from outside the compose network by construction, the same pattern the internal port already uses, so a scraper never needs a token or a cluster certificate.

A key's `N` replicas are chosen by consistent hashing (150 virtual nodes per real node). Writes and reads fan out concurrently to the preference list and return once `W`/`R` of them respond. Each value carries a vector clock; concurrent, causally-unrelated writes are surfaced as a 409 with both versions rather than silently resolved. A replica that's down when a write lands gets its write handed to a neighbor (a "hint"), delivered once gossip reports it's back.

## Running it

```bash
python scripts/gen_certs.py   # once: generates the cluster CA + per-node certs into certs/
docker compose up --build
```

Three nodes come up on `https://localhost:8001`, `:8002`, `:8003`. `docker compose down -v` tears the cluster (and its data volumes) down.

## API reference

Full interactive OpenAPI/Swagger docs are auto-generated by FastAPI at `/docs` on any node's public port (e.g. `https://localhost:8001/docs`).

```bash
TOKEN=tok_demo_admin   # see auth_tokens.json for demo tokens/permissions

curl -sk -X PUT https://localhost:8001/v1/keys/hello \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"value": "world"}'

curl -sk https://localhost:8001/v1/keys/hello -H "Authorization: Bearer $TOKEN"

curl -sk -X DELETE https://localhost:8001/v1/keys/hello -H "Authorization: Bearer $TOKEN"
```

`GET /healthz` (no auth, unversioned) reports node identity and liveness. Keys are namespaced by an optional `namespace:` prefix (e.g. `orders:42`) — see `auth_tokens.json` for which demo tokens can read/write/delete which namespace.

## Design decisions

- **N=3, R=2, W=2.** A read and a write quorum are guaranteed to overlap (`R + W > N`), so a successful write is never invisible to a subsequent read under normal operation — the same pigeonhole guarantee the Dynamo paper leans on. This is a deliberate **availability-over-consistency** choice (the CAP trade-off Dynamo is famous for): a write succeeds as soon as 2 of 3 replicas ack, even if the third is down or partitioned, rather than blocking for unanimous agreement.
- **Vector clocks, not timestamps**, detect genuine concurrent writes (as opposed to a stale read racing a fresh write, which "presence beats absence" reconciliation already handles for free). A real conflict — two writes neither of which causally precedes the other — surfaces to the client as a 409 with both versions, rather than being silently resolved by last-write-wins.
- **Two ports, two trust domains, not one.** mTLS on every request would force real clients to hold a cluster certificate just to make a GET; token auth on internal replica traffic would require every node to also manage revocable client credentials for its peers. Splitting them means the public API authenticates however a client naturally would (bearer token) while internal traffic authenticates however a cluster member naturally would (mTLS) — confirmed necessary rather than assumed: standard ASGI/uvicorn doesn't expose a negotiated client certificate to route handlers, so "mTLS only on some routes, same port" isn't actually available as a simpler alternative.
- **Encryption at rest wraps the storage interface, not the application.** `EncryptedStorage` implements the same `StorageBackend` protocol every other backend does, so nothing above the storage layer knows or cares that values are encrypted on disk.
- **`/metrics` gets its own unpublished port** rather than living unauthenticated on the public port or behind the internal mTLS port — the former exposes operational data to anyone who can reach the client API at all; the latter would require a scraper to hold a cluster client certificate just to read a counter. A third, compose-network-only port gets the same "no per-request auth needed" property as the internal port without either downside.

## Security testing

Phase 7 built an adversarial testbed (`scripts/adversarial_testbed.py`) that red-teams the security layer as an integrated live system rather than re-proving each mechanism in isolation, from a "compromised node" insider-threat model: 10 attack categories, each executed against the real running 3-node cluster. Last measured run: **11/18 scenarios prevented (61%), 6/18 detected (33%)** — prevention and detection are tracked independently, since a scenario can be neither, either, or both. Full results and the reasoning behind every UNDEFENDED finding are in `reports/phase7_adversarial_report.md` and `PROGRESS.md`'s Phase 7 entry.

## Benchmarking against real DynamoDB

Phase 8 (`scripts/dynamodb_bench.py`) compares this system's latency/throughput against a real AWS DynamoDB table at matched consistency tiers (eventually-consistent and quorum/strongly-consistent reads, PutItem writes), across several value-size tiers, with network RTT to AWS measured and reported separately from database processing time. Code and local tests are complete; the live run against a real AWS account is pending credentials — see `PROGRESS.md`'s Phase 8 entry for the full methodology and honest-accounting caveats.
